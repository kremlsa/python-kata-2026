Конспект: строки, Unicode, валидация и Path Traversal
1. Строки и байты
- str — последовательность кодовых точек Unicode.
- bytes — последовательность байтов.
- encode() — преобразование строки в байты.
- decode() — преобразование байтов в строку.
- len(str) — количество кодовых точек, а не размер в байтах.
value = "пароль"len(value)                  # 6len(value.encode("utf-8"))  # 12



UTF-8 кодирует одну кодовую точку в 1–4 байта.
Неизменяемость строк
Строки — immutable. При изменении значения создаётся новый строковый объект.
a = "admin"b = aa += "_user"print(a)       # admin_userprint(b)       # adminprint(a is b)  # False



2. Unicode и нормализация
Визуально одинаковые строки могут состоять из разных кодовых точек.
import unicodedataa = "\u00e9"    # éb = "e\u0301"   # e + combining accentprint(a == b)  # Falseunicodedata.normalize("NFC", a) == \unicodedata.normalize("NFC", b)  # True



Основные формы:
Форма	Назначение
NFC	Каноническая композиция
NFD	Каноническая декомпозиция
NFKC	Совместимая композиция
NFKD	Совместимая декомпозиция

AppSec: нормализация не гарантирует устранения похожих символов (homoglyphs). Латинская a и кириллическая а остаются разными после NFC.

Для ограниченных идентификаторов лучше применять allowlist допустимых символов.
3. Валидация строк
Реализовали валидатор API-токена с требованиями:
- Тип строго str.
- Длина от 8 до 32 символов.
- Допустимы ASCII-буквы, цифры, _ и -.
- Без изменения регистра и удаления пробелов.

4. URL Encoding и каноникализация
urllib.parse.unquote() выполняет URL-декодирование.
from urllib.parse import unquoteunquote("%2e%2e%2fsecret.txt")# ../secret.txt



Double URL Encoding:
value = "%252e%252e%252fsecret.txt"first = unquote(value)# %2e%2e%2fsecret.txtsecond = unquote(first)# ../secret.txt



Уязвимость возникает, когда валидация применяется к одному представлению данных, а их использование — к другому.

Принцип: преобразования входных данных должны быть однозначными и согласованными между компонентами. Нельзя безусловно декодировать данные повторно до исчезновения всех %.
5. Path Traversal
Опасный подход:
if "../" in filename:    raise ValueError



Недостатки: не учитывает все варианты представления пути, абсолютные пути, особенности ОС и символические ссылки.

Для контроля расположения файла можно использовать:
from pathlib import PathBASE_DIR = Path("/app/documents").resolve()requested = (BASE_DIR / filename).resolve()if not requested.is_relative_to(BASE_DIR):    raise ValueError("Access denied")



- resolve() — вычисляет разрешённый абсолютный путь, включая обработку .. и символических ссылок.
- is_relative_to() — проверяет, находится ли полученный путь внутри базового каталога либо совпадает с ним.
Это полезная проверка, но она не устраняет TOCTOU, если злоумышленник может изменять файловую систему.
6. TOCTOU
Time-of-Check to Time-of-Use — изменение состояния объекта между проверкой и использованием.

Пример:
1. Приложение проверяет /app/documents/report.txt.
2. Путь находится внутри разрешённого каталога.
3. Атакующий заменяет файл символической ссылкой на /app/secrets.txt.
4. Приложение открывает файл, переходя по ссылке.
Причина: проверяется путь, но между проверкой и открытием объект файловой системы может измениться.

Защитные подходы:
- Ограничивать возможность изменения защищённых каталогов.
- Использовать операции с файловыми дескрипторами вместо повторного разрешения строковых путей.
- На Linux использовать openat2() с соответствующими ограничениями разрешения пути.
- Не считать повторный resolve() полноценной защитой от гонки.
